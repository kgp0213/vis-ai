## 一、背景与问题发现

### 1.1 起因

检查"从 JSON 导入模型配置后的压缩阈值相关功能设定是否需要优化"。经对 5 个核心源文件逐行核实，发现 6 个主要问题：

1. 导入后上下文 cap 不会立即刷新
2. 固定比例阈值对大上下文模型不友好
3. maxContextLength 和压缩 cap 被混为一谈
4. 预检只折叠一次，没有循环检查
5. 摘要模型可能选到昂贵模型
6. Dashboard 下拉框与模型默认值可能不匹配

### 1.2 源码核实结论

- dist 文件行号（chunk-2R4QCDOZ.js、server-XGDBRWMB.js、app.js）全部精确匹配
- launcher.mjs 行号全部有误（偏差 26~185 行），但逻辑判断均正确
- 所有 6 个问题经源码确认属实

## 二、配置体系全景

### 2.1 配置数据源

**磁盘配置** ~/.visionox/config.json

| 字段 | 说明 |
|---|---|
| apiKey / baseUrl | 全局 API 凭据（legacy 模式） |
| model | 基线模型 ID（仅 preset=auto 时生效） |
| preset | 预设档位：auto / flash / pro |
| reasoningEffort | 推理力度：max / high |
| contextCapTokens | 手动压缩阈值覆盖（导入时清空） |
| activeProviderId | 当前激活的 provider ID |
| providers[] | provider 列表，每项含 models[] |

**硬编码默认值** (chunk-YQ6NTIIE.js)

- DEEPSEEK_CONTEXT_TOKENS：所有 DeepSeek 模型 = 1e6 (1M)
- DEFAULT_CONTEXT_TOKENS = 131072 (128K)

**运行时全局变量** (由 launcher.mjs 设置)

- DEEPSEEK_CONTEXT_TOKENS[model]：运行时实际上下文上限
- globalThis.__visionoxSummaryModel：折叠摘要使用的模型 ID
- globalThis.__visionoxThinkingModeMap：各模型 thinking 模式映射

### 2.2 上下文容量优先级链

1. config.contextCapTokens（手动覆盖）— 用户设置页手动设定；JSON 导入时清空
2. modelObj.maxContextLength（JSON 导入的模型上限）— 从激活 provider 的 models 中查找当前 model
3. DEEPSEEK_CONTEXT_TOKENS[model]（硬编码表，DeepSeek = 1M）
4. DEFAULT_CONTEXT_TOKENS = 131072（128K）

行为保证：导入即重置 -> 手动即覆盖 -> 再次导入再重置。

### 2.3 压缩阈值与折叠逻辑（优化后）

阈值常量（chunk-2R4QCDOZ.js:6589-6601）：

| 常量 | 比例值 | 绝对上限 | 说明 |
|---|---|---|---|
| HISTORY_FOLD_THRESHOLD | 0.5 (50%) | 200000 | 开始普通折叠 |
| HISTORY_FOLD_AGGRESSIVE_THRESHOLD | 0.7 (70%) | 280000 | 激进折叠 |
| FORCE_SUMMARY_THRESHOLD | 0.8 (80%) | 320000 | 强制摘要退出 |
| PREFLIGHT_EMERGENCY_THRESHOLD | 0.95 (95%) | 380000 | 预检紧急折叠 |
| HISTORY_FOLD_TAIL_FRACTION | 0.2 | 40000 | 普通折叠 tail 预算 |
| HISTORY_FOLD_AGGRESSIVE_TAIL_FRACTION | 0.1 | 20000 | 激进折叠 tail 预算 |

有效阈值 = min(比例值, 绝对上限 / ctxMax)。小上下文模型（<=200K）行为不变，大上下文模型（1M）在 200K 就开始折叠。

双阈值效果对比：

| 模型 | 修改前折叠点 | 修改后折叠点 | tail 预算变化 |
|---|---|---|---|
| 128K | 64K (50%) | 64K (50%) 不变 | 26K 不变 |
| 1M | 500K (50%) | 200K (19.1%) | 40K（原 200K） |
| 1M 激进 | 700K (70%) | 280K (26.7%) | 20K（原 100K） |
| 1M 强制摘要 | 800K (80%) | 320K (30.5%) | - |
| 1M 紧急预检 | 950K (95%) | 380K (36.2%) | - |

决策点 1：回合后检查 decideAfterUsage — 每次模型回复后根据 promptTokens / ctxMax 决策：大于 80% 强制摘要退出，大于 70% 激进折叠，大于 50% 普通折叠。

决策点 2：发送前预检 decidePreflight — 发送请求前估算 token 总量，大于 95% 紧急折叠。优化后增加二次检查：第一次折叠后重新 decidePreflight，若仍超 95% 则第二次激进折叠（keepRecentTokens=0），若仍超限输出 preflightStillOver 警告。

### 2.4 摘要模型选择逻辑（优化后）

优先级：flash/lite/mini 模型 > maxContextLength 最小的模型 > 第一个模型 > 硬编码 "deepseek-v4-flash"。

设置时机：buildLoop() 和 refreshContextCap() 中都会设置。

### 2.5 模型切换机制

| 切换类型 | API | 服务端处理 | 广播事件 |
|---|---|---|---|
| 预设切换 | POST /settings | applyPresetLive | config-changed |
| 模型切换 | POST /settings | applyModelLive | config-changed |
| Provider 切换 | POST /providers/active | syncProvider (重建 loop) | config-changed |
| JSON 导入 | POST /providers/import | 合并+清空cap+refreshContextCap | config-changed |
| 阈值修改 | POST /settings | refreshContextCap | config-changed |

### 2.6 UI 联动事件流

用户在 UI 操作 -> POST /api/settings 或 /api/providers/import -> server: writeConfig + applyModelLive/refreshContextCap -> launcher.mjs: applyContextCap 更新 DEEPSEEK_CONTEXT_TOKENS -> launcher.mjs: broadcastDashboardEvent({ kind: "config-changed" }) -> SSE 推送到 dashboard -> app.js: config-changed 处理器立即 GET /overview -> 状态栏即时更新模型名、上下文容量、压缩阈值标记。

### 2.7 上下文容量刷新触发点

| 触发场景 | 调用链 |
|---|---|
| 启动 / /new / 工作区切换 | buildLoop() -> applyContextCap() |
| 预设切换 | applyPresetLive() -> applyContextCap() |
| 模型切换 | applyModelLive() -> applyContextCap() |
| 压缩阈值手动修改 | POST /settings -> refreshContextCap() -> applyContextCap() |
| JSON 导入 | POST /providers/import -> refreshContextCap() -> applyContextCap() |
| Provider 切换 | syncProvider() -> buildLoop() -> applyContextCap() |

## 三、三轮优化改动明细

### 第一轮：核心功能修复（P0/P1/P2）

#### P0：导入后立即刷新压缩阈值

问题：server-XGDBRWMB.js:3205-3227 的导入处理器只写磁盘、清空手动 cap，不刷新运行中 loop。

修复：
- launcher.mjs: 新增 refreshContextCap 方法到 ctx 对象（行 2866-2879）
  - 重读配置 -> syncRuntimeConfig -> 清除 stale cap -> applyContextCap -> loop.configure -> broadcastDashboardEvent
- server-XGDBRWMB.js: 导入处理器 writeConfig 后调用 ctx.refreshContextCap()（行 3226）

测试：服务器日志确认 "context cap refreshed: model=deepseek-v4-flash, cap=1048576"；手动设置 contextCapTokens=32768 后导入，配置中 contextCapTokens 被清空为 null。

#### P1：预检折叠后二次检查

问题：chunk-2R4QCDOZ.js:7958-7992 折叠后不重新 decidePreflight，仍超 95% 会直接发送导致 API 400。

修复：
- chunk-2R4QCDOZ.js: 折叠后增加 re-check 逻辑（行 7981-8001）
  - 第一次折叠后重新 decidePreflight
  - 若仍超限，第二次激进折叠（keepRecentTokens=0）
  - 若仍超限，输出 preflightStillOver 警告
- chunk-RE4RAVFF.js: 新增 preflightStillOver 翻译键（英文+中文）

测试：语法检查通过，decidePreflight 调用数 4（1 定义 + 3 调用）。

#### P2：摘要模型选择优化

问题：launcher.mjs:2096 取 provider.models[0].id 做摘要模型，可能是昂贵的 pro 模型。

修复：launcher.mjs:2099-2102 改为优先选择 flash/lite/mini，其次 maxContextLength 最小，最后回退第一个。

测试：5 个单元测试用例全部通过。

### 第二轮：UI 联动修复（GAP 1/2/3）

#### GAP 1：设置页改 contextCapTokens 不即时生效

问题：server-XGDBRWMB.js 设置 POST 处理器只写磁盘，不调 refreshContextCap，运行中 loop 的 cap 不更新。

修复：server-XGDBRWMB.js:3468 在 contextCapTokens 变更后调用 ctx.refreshContextCap()。

测试：设置 contextCapTokens=65536 -> 日志 "cap=65536" 立即生效；清除 -> 日志 "cap=1048576" 回退。

#### GAP 2：模型/预设/cap 切换不广播事件

问题：applyModelLive/applyPresetLive/refreshContextCap 修改运行时状态后不广播，UI 靠 5 秒轮询。

修复：launcher.mjs 在 applyPresetLive(行2846)、applyModelLive(行2861)、refreshContextCap(行2878) 末尾添加 broadcastDashboardEvent({ kind: "config-changed" })。

测试：SSE 流中捕获到 config-changed 事件。

#### GAP 3：前端不处理 config-changed 事件

问题：聊天界面的 EventSource 没有 config-changed handler，状态栏延迟最多 5 秒。

修复：
- app.js:23989 主聊天界面添加 config-changed handler -> 立即 GET /overview 更新 stats/overviewModel/preset/effort 等
- app.js:30648 备用聊天界面添加 config-changed handler -> 立即 GET /overview 更新 stats/model
- app.js:24473 setSetting 成功后额外拉取 /overview 更新 stats/overviewModel

### 第三轮：全面优化（7 项）

#### 1. syncProvider 添加 broadcastDashboardEvent（高优先级）

问题：Provider 切换重建整个 loop 但不广播事件，状态栏延迟 5 秒。

修复：launcher.mjs syncProvider 末尾添加 broadcastDashboardEvent({ kind: "config-changed" })。

测试：切换 provider 时 SSE 捕获到 2 个 config-changed 事件。

#### 2. 更新 appliesAt 指示器 + UI 文本（高优先级）

问题：修复后 contextCapTokens 已即时生效，但提示仍显示"重启或 /new 后生效"。

修复：
- server-XGDBRWMB.js: contextCapTokens "next-session" -> "live"，preset "next-session" -> "live"，model "next-turn" -> "live"
- app.js:28155 "重启或 /new 后生效" -> "即时生效"

测试：API 返回值确认三个字段均为 "live"。

#### 3. 下拉框支持非标准值（中优先级）

问题：下拉框只有 32K/64K/128K/256K/1M，非标准值（如 81920）不匹配。

修复：
- app.js: value 逻辑从 contextCapTokens ?? providerContextCap ?? "auto" 改为 contextCapTokens ?? "auto"
- "模型默认" 选项动态显示实际值：模型默认 (80K)
- 非标准手动值动态添加对应 option

#### 4. 大上下文模型双阈值（中优先级）

问题：1M 窗口模型 50% = 500K 才折叠，太晚。

修复：chunk-2R4QCDOZ.js 添加绝对上限常量，有效阈值 = min(比例, 绝对上限/ctxMax)。
- 新增 HISTORY_FOLD_ABSOLUTE_CAP=200000 等 6 个绝对上限常量
- 修改 decideAfterUsage、decidePreflight、fold 使用有效阈值/预算

测试：128K 模型行为不变，1M 模型在 200K 折叠（原 500K），tail 预算 40K（原 200K）。

#### 5. cap 校验不超过 maxContextLength（中优先级）

问题：用户可设置 cap 超过模型实际上限，导致 API 400。

修复：server-XGDBRWMB.js:3409-3418 在设置 contextCapTokens 时校验是否超过 modelObj.maxContextLength。

测试：设置 2M cap 当模型上限 1M -> 返回 400 错误；设置 64K -> 成功。

#### 6. refreshContextCap 中更新 summaryModel（低优先级）

问题：__visionoxSummaryModel 仅在 buildLoop 中设置，导入后不更新。

修复：launcher.mjs refreshContextCap 中添加摘要模型重新选择逻辑。
