## 1. 发布决策

当前源码已经通过完整 Node/UI 质量门禁，并由规范流程生成 Release EXE 与 NSIS 安装包。版本、运行资源、第三方清单和安装包资源的一致性均有自动化保护，代码质量基础满足进入安装验收阶段的条件。

安装版升级和长会话回归仍需用户在真实安装环境中完成。通过这些人工验收前，不应创建发布 tag 或对外分发安装包。

## 3. 发布阻塞项

### P0-1：冻结并提交可追溯源码（本次提交处理）

1. 审查完整 `git diff` 和所有未追踪源码，确认没有临时诊断文件、旧实现或用户数据。
2. 保持 `docs/CHANGELOG.md` 与实际资源数量一致；当前为 42 个技能、22 verified、20 partial。
3. 运行 `npm run quality:check`，通过后提交全部计划发布的源码。
4. 记录完整 commit SHA，并确认工作树只保留明确不参与发布的变更；最稳妥的状态是完全干净。
5. 从该 commit 执行 `npm run release:check`。若之后任何运行时代码或资源改变，前述结果失效，必须重新执行。

验收标准：发布记录中的 commit 能完整重建同一版本，`git diff --check` 和全部门禁通过。

### P0-2：生成并验证真实安装包（已完成）

已按用户授权使用：

```powershell
npm run bundle:nsis
```

该命令必须同时通过 `verify:nsis`，确认安装包内 EXE 与 Release 仅存在允许的 Tauri marker 差异，并逐文件核对完整 `resources/`。禁止手工替换 EXE、复制资源或从旧安装目录补文件。

结果：安装包文件名、大小和 SHA-256 已记录，自动资源校验无缺失、无额外文件。

### P0-3：完成安装版而非裸 EXE 的回归

必须由用户自行安装，并明确从安装目录启动。至少覆盖：

| 场景 | 必须确认的结果 |
|---|---|
| 全新安装 | 默认浅色主题；未配置模型时有清晰入口；用户数据目录创建正常；不依赖源码目录、系统 Node 或 Python |
| 旧版覆盖升级 | 原有会话、模型配置、Soul、记忆、定时任务和工作区历史保留；不重复生成资源副本 |
| 长会话 | 恢复超过 1000 条消息的真实会话后，输入、滚动和切换无明显卡顿，界面宽度不跳动 |
| 模型 | JSON 导入、全模型检测、通过标识、首个通过模型自动启用；外部 DeepSeek 与内部单模型分支不互相破坏 |
| 索引与知识 | 三种索引模式保持；工作区和 `knowledge/` 可构建、搜索和自动召回 |
| 会话整理 | AI 质量评估、低价值过滤、同主题合并、知识归档及可选 embedding 更新正常 |
| 数据管理 | 会话/记忆回收站可预览、恢复、永久删除；用户数据快照可创建、预览且默认不覆盖冲突 |
| 内置资源 | OfficeCLI、KaTeX、Tavily、bootstrap skills 和 ECC 在没有源码仓库的环境可用 |
| 退出清理 | 主程序退出后，其所属 Node 和 OfficeCLI 子进程全部结束 |

验收标准：裸 EXE 和安装版对同一长会话表现一致；安装版不得再次出现“资源内容不同导致性能或功能回退”。

### P0-4：处理第三方来源的发布边界

当前技能来源门禁允许 `partial` 状态，但 42 个技能中仍有 20 个来源或许可证未完全核验。这不影响内部功能测试，却可能影响公开或对外分发。

- 内部分发：由项目负责人明确接受并记录该风险。
- 对外或商业分发：发布前补齐这些技能的来源和许可证，或从安装包移除无法确认授权的技能。

验收标准：发布记录明确分发范围，并对所有随包资源具有可解释的授权依据。

## 4. 关键功能状态复盘

以下历史问题已有源码和自动化测试覆盖，不再作为“待确认修复”重复列项：

- `@skill` 和 `/skill` 为结构化确定性调用；完整技能名称始终注入，`run_skill` 直接读取当前技能存储。4000 字符限制只裁剪低优先级技能详情，不会阻止显式调用。
- 工作区切换使用服务端历史和原生目录选择器，并在新会话边界应用待切换工作区。
- 会话与记忆回收站支持批量操作、预览、恢复、永久删除和自动过期清理。
- ECC 配置按当前工作场景保存并立即刷新上下文。
- Tavily 首次使用提供本地 API Key 输入流程；内置实现随 Release 发布并使用打包 Node，不要求系统 Python。
- Release 运行时只由规范资源准备与校验流程生成，`{baseDir}` 在技能调用时解析为实际部署目录。

仍需关注的是这些功能在“安装版”中的真实表现，不能用源码测试或裸 Release EXE 替代第 3 节的安装验收。

## 5. 产品与用户体验验收

从产品角度，v1.28.0 的发布标准不只是“能启动”，还应满足以下结果：

1. **首次使用可完成**：用户能在不理解 Provider JSON 结构的情况下导入、检测并开始对话；Tavily 缺少凭据时能在当前操作位置完成配置。
2. **已有数据可信**：升级后不丢会话、不改变用户主动选择的索引模式和工作模式，不因资源部署覆盖用户自建同名技能。
3. **错误可处理**：启动失败、模型不可用、索引缺失和存储保护问题给出具体动作，不向普通用户暴露无意义的技术噪声。
4. **高频路径稳定**：长会话输入、模型切换、工作区切换、新建会话和回收站操作不产生布局跳动或重复确认干扰。
5. **版本可识别**：概览、日志和安装包文件名显示一致的 `1.28.0`；用户能够判断当前运行的是安装版还是测试 EXE。

自动更新不是 v1.28.0 的发布阻塞项。当前产品采用手动更新，应在发布渠道同时提供版本号、变更摘要、安装包哈希和升级说明；以后是否接入自动更新应作为独立产品决策，不应临时塞入本次发布。

## 6. 安全与数据风险

### 已有控制

- Tauri 主窗口仅声明 `core:default` capability；服务地址强制为 `127.0.0.1` 动态端口。
- Release 对 Node、OfficeCLI 和完整资源树做版本、大小及 SHA-256 校验。
- 关键用户数据采用原子写入、版本校验或损坏保护；备份恢复默认不覆盖冲突。
- 日志包含凭据脱敏规则；Tavily 密钥不会写入聊天记录或返回给前端明文读取。
- `currentUser` 安装符合本产品不要求管理员权限的定位，本身不应被描述为安全缺陷。

### 已知且需接受的风险

- 模型和 Tavily 凭据保存在当前用户目录的本地配置文件中。Unix `0600` 不能等价为 Windows ACL；若产品未来面向高安全场景，应独立评估 Windows Credential Manager 或 DPAPI。此项不建议在 v1.28.0 发布前仓促改动。
- CSP 仍包含 `unsafe-inline`、`unsafe-eval` 和 localhost 通配。当前 Dashboard bundle 与本地服务架构依赖这些配置，收敛前必须先建立 CSP 回归测试，不能只删除字符串。
- 内网 embedding 凭据按项目约定不视为敏感凭据；仍应避免把它误显示在普通 UI、日志或对话上下文中。
- Dashboard/API 仍包含受补丁门禁保护的上游 bundle 修改。`check-bundle-patches` 能防止补丁被升级覆盖，但长期维护成本仍高，应继续按 `DASHBOARD_PARITY.md` 推进可重建源码迁移。

## 7. 兼容性与回退

- 保留 `com.visionox.desktop` 和 `%USERPROFILE%\.visionox\`，避免品牌改名导致用户数据迁移。
- v1.28.0 当前只应承诺 Windows x64。Linux 资源配置尚未与 Windows 主配置完全对齐；未完成独立构建和验收前不得宣称支持 Linux 发布。
- 安装前通过概览创建用户数据快照，并记录快照健康状态。保留上一稳定版本安装包、commit、版本号和 SHA-256。
- 应用程序可以回退，用户数据不应假设天然向后兼容。若新版本已经写入更高 schema 的数据，旧版本可能拒绝读取；回退演练必须同时验证相应版本的数据快照恢复方案。
- 不应依赖“卸载再安装”作为数据恢复措施，卸载行为和用户数据保留必须单独验证。

## 8. 推荐发布顺序

1. 冻结 v1.28.0 范围，审查完整 diff，修正文档数量和来源状态。
2. 执行 `npm run quality:check`，提交计划发布的全部源码。
3. 记录完整 commit SHA，确认工作树状态符合发布记录。
4. 在该 commit 上执行 `npm run release:check`，完成隔离 Rust 测试和规范 Release 重建。
5. 对 Release EXE 完成功能抽查，记录大小和 SHA-256。
6. 获得明确授权后执行 `npm run bundle:nsis`，保存自动验证输出。
7. 用户自行完成全新安装和旧版覆盖升级测试，重点复测千条长会话与资源完整性。
8. 更新 `RELEASE_CHECKLIST.md` 的 commit、环境、功能结果和两个产物哈希。
9. 发布负责人签字确认后，在验收通过的 commit 上创建 `v1.28.0` annotated tag。
10. 获得明确授权后再推送 commit/tag、上传安装包或对外发布。
