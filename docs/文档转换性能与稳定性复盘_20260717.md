# 文档转换性能与稳定性复盘（2026-07-17）

> 历史复盘：本文记录 2026-07-17 的文档专用后台方案，不再代表当前架构主线。2026-07-20 起以
> `plan/complex-task-state-machine-primary-goals.md` 为准：简单任务使用普通模型工具循环，复杂任务由通用
> 状态机监督同一个执行内核；PDF、Word 等格式 Adapter 不得拥有独立任务生命周期。文中的
> `organize_document_to_markdown`、`extract_pdf_text` 和 PDF 自动续读说明仅用于追溯旧行为。

## 结论

大型 PDF、Word、Excel、PowerPoint、HTML、Markdown、CSV 和文本文件不应依赖模型在聊天轮次中自行完成“读取全部内容、总结、写文件”。当前版本采用宿主管理的可恢复文档任务：确定性抽取、稳定分块、模型整理、独立审校、定向重试、来源校验和最终原子写盘彼此分离。

因此，旧报告中“模型一次性 `write_file` 导致中间页丢失”的结论只适用于旧链路，不能再作为当前主因。当前最重要的质量边界是：每次模型响应是否明确完成、主模型是否被备用模型的限制拖慢，以及任务状态是否足够可观测。

## 已落地的保护

| 领域 | 当前行为 | 解决的问题 |
| --- | --- | --- |
| 来源准备 | `prepareLocalDocument(s)` 生成稳定来源引用；文件、页、幻灯片、工作表都有来源前缀 | 避免路径歧义、页段错位和跨文件混淆 |
| 抽取与分块 | PDF 按完整页边界交付，Office/HTML 等按稳定单元交付；跨边界只提供只读上下文 | 避免关键句恰好跨两个区块时被截断 |
| 质量检查 | 程序化覆盖/长度/技术值保留检查 + 独立模型审校 + 定向修复 | 不把“模型返回了文字”误认为高质量完成 |
| 保存 | 区块检查点、section 文件、manifest 和来源 SHA-256；最终由宿主原子组装 | 模型不能用一次超长 `write_file` 丢失正文 |
| 恢复 | 任务可暂停、继续、立即停止、放弃、预览、重试失败区块；重启后恢复安全检查点 | 中断不再等同于从头开始或静默失败 |
| 多文档 | `organize_documents_to_report` 一次接收完整集合，保留每个来源边界并在提交前重新校验全部来源 | 避免把相关文件拆成互不关联的摘要 |
| 模型响应 | SSE/非流式响应记录 `finish_reason`；`length`、内容过滤和不完整流进入可重试失败 | 输出达到上限时不会直接提交为成功 |
| 主备模型 | 初始分批只按 primary 策略；只有失败区块切到 fallback 时才按 fallback 限制拆分 | Qwen 的小批次限制不会拖慢整份 DeepSeek 任务 |
| Provider 能力 | `multimodal`、`visionPolicy`、`escalationModel` 取自 JSON；不再固定使用 DeepSeek Pro | 内网模型升级时不必修改程序硬编码 |
| 任务观测 | 记录用途、provider/model、区块、尝试次数、耗时、输出量、finish reason 和模型角色；后台工作台展示累计/当前进度 | 区分“当前区块调用数”和“整份任务调用数” |
| 工具容错 | 截断 JSON 修复仅生成内部报告；桌面只显示脱敏的修复次数，不回显参数、路径或密钥 | 弱模型自修复不再完全静默，也不泄露敏感内容 |
| 通用工具 | `read_file` 明确是 UTF-8 文本读取；Shell 输出保留开头和滚动尾部 | 避免模型误用文本工具读取二进制，或看不到错误尾部 |

## 推荐调用契约

单文件保存型转换只调用一次 `organize_document_to_markdown`：

```json
{
  "input": "C:\\path\\source.pdf",
  "outputPath": "C:\\path\\source-整理.md",
  "fidelity": "complete-with-summary",
  "instructions": "保留表格、参数、命令和图示说明"
}
```

跨文件比较、合并或综合报告只调用一次 `organize_documents_to_report`：

```json
{
  "inputs": ["C:\\path\\spec.docx", "C:\\path\\results.xlsx"],
  "outputPath": "C:\\path\\combined-report.md",
  "fidelity": "complete-with-summary",
  "instructions": "按来源分别引用证据，再给出差异结论"
}
```

模型不应为同一个保存请求手动串联 `prepare_local_document`、`extract_pdf_text`、OfficeCLI、`read_file`、`write_file` 或 `append_file`。后台任务接单后当前聊天轮次结束，用户通过“后台”工作台查看状态；“已接单”不等于“文档已经完成”。

超过 3000 页的 PDF 会返回结构化选择，模型必须调用 `ask_choice` 让用户选择页段或分卷，不得在正文中伪造菜单。只读查看 PDF 仍使用 `prepare_local_document` + `extract_pdf_text`，收到 `complete=false` 时沿用同一个 `documentRef` 读取 `nextPageRange`。

## 为什么 DeepSeek 与 Qwen 速度不同

旧实现把所有候选模型的限制取最小值。例如 Qwen 的 `batchOutputTokens=3000` 会把 DeepSeek 主模型也压成小区块，进而增加整理、审校和重试次数。当前 `effectiveDocumentPolicy` 只从 primary 候选计算初始策略；fallback 仅在失败区块上生效，并把拆分原因、父区块和策略写入事件与检查点。

这不意味着应把 DeepSeek 标成视觉模型。`providers-0717.json` 中图片能力必须以实际接口支持为准：没有 `multimodal` 的模型不会收到 `image_url`；Qwen 的 `visionPolicy`、图片数量和上下文预留由 JSON 声明。

## 可观测性与用户提示

后台工作台应同时显示：

- 当前来源、页/元素范围和完成条件；
- 当前区块调用数/上限与整份任务累计调用数；
- 主模型、备用模型、切换原因和每次尝试耗时；
- `length`、超时、质量失败、待复核等可行动状态；
- 已保存草稿、最终产物和可继续位置。

模型返回不完整工具参数时，聊天区只显示类似“模型返回的工具调用格式不完整；系统已自动修复了 1 次工具参数格式，任务继续执行。”的短提示。参数原文、内部 `notes`、路径和凭据只进入受控日志或不记录。

## 从旧稳定性报告吸收的内容

`vis-ai-文档转换稳定性分析.md` 对以下问题的判断仍然有效，并已吸收：

1. 必须消费 `finish_reason`，不能把达到输出上限的响应当成正常成功。
2. 空 SSE 帧不能结束整条流；坏 JSON 帧不能静默变成成功。
3. 截断 JSON 修复应有边界、可审计，并向用户给出低噪声提示。
4. 文档正文不能依赖聊天上下文、上下文折叠或一次性工具参数保存。
5. Provider 能力和模型名称不能写死在 DeepSeek 专属分支中。

报告中以下结论已过期或不应照搬：

- “项目没有专用文档转换流程”不再适用，当前已有宿主状态机和检查点。
- 没有证据时不能把所有模型上下文降到 32K；应以 JSON 声明、网关文档或受控探测为准。
- 不能为了绕过图片问题把不支持视觉的 DeepSeek 模型标成 `multimodal: true`。
- 不能靠无限增加聊天工具轮次解决大文档任务；应继续使用后台区块任务。

## 验收与剩余风险

源码门禁包括专项文档、模型流、Provider、DLP、任务恢复和 Dashboard 测试，以及 `node --check`、bundle 补丁检查、`npm test` 和 `npm run quality:check`。故障注入测试覆盖：输出上限、坏流、超时、重复恢复、来源变化和跨文档集合。

本机无法直接验证内网 Qwen 服务时，必须依赖这些离线测试和另一台可访问 Qwen 的机器做最终验收。发布前仍需在 release 资源树中确认 bundle 与源码同步；未经用户明确要求，本轮不构建 release 或安装包。

真实 Provider JSON 可能包含 API Key，只能保留在本机并由 `.gitignore` 排除；文档和测试不得写入密钥、完整模型响应或用户原文副本。
